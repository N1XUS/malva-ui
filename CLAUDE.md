- [docs/migrations/2026-09-select-native-auto-hydration.md](docs/migrations/2026-09-select-native-auto-hydration.md) — **breaking, behaviour only** (no exported symbol renamed or removed; no input, output, model, token, i18n key or BEM class change): a `mlv-select native="auto"` that hydration claims now renders the server's native `<select>` for its first client render and, at or above `md`, switches to the custom trigger inside the same application tick. Before, a desktop client resolved the trigger from its viewport on that first render — no NG0500, nothing logged — building it beside the unclaimed server `<select>`, so two elements carried the field's id and a dead transparent `<select>` covered the live trigger until `cleanupDehydratedViews` removed it at stability. "Being hydrated" has no public Angular API: the select reads the internal `ngh` host attribute in a field initializer (Angular strips it in `renderComponent` after directive construction; a tripwire spec guards it), so a client-only app, a dialog, an `@if` after hydration and an `ngSkipHydration` subtree resolve `'auto'` from the viewport from their first render, exactly as before (their native-mode trigger also loses `id="null"`). Shipped as `!` because documented outcomes inside that render now arrive differently: for that render `labelTarget().labelable` is `true`, the host carries `--native` and the label `for`; `openDropdown()` / `toggleDropdown()` called during it reach the end state they reached before only once the switch lands (`isOpen()` is `false` on return), including when `native` turns `false` in between; focus on the claimed `<select>` — placed before JavaScript ran, by a later after-render hook such as `cdkTrapFocusAutoCapture`, or by `openDropdown()` — is handed to the trigger with no `touch`, as it is for any hydrating select (`native="true"` and phones included) whose `native` turns `false` during that render, and of two hydrating selects focused in turn the one focused last keeps it. The server now renders `'auto'` native whatever its breakpoint service answers, and every native-mode trigger (server and browser, `'auto'` and `true`) loses its stray `id="null"`: assert `!trigger.hasAttribute('id')`. Hydrating phones and `native="true"` load a lazy `searchFn` at the same point as before, as does a hydrating desktop whose `native` or viewport answer changes during that render. Left open: `openDropdown()` followed by `isOpen.set(false)` in that render still opens, and followed by `disabled` turning `true` it ends closed; a later `md` crossing, or `native` turning `false`, that removes a focused `<select>` still drops focus and, in Chromium, marks the field touched (jsdom fires no `blur`, so `focused()` stays `true`); event replay of a pre-JS native choice and `hydrate on interaction` are unverified; and `mlv-sidebar`, `mlv-page-end-pane` and `*mlvBreakpointDown/Up` carry the same server/client mismatch.
- [docs/migrations/2026-09-fluid-heading-scale.md](docs/migrations/2026-09-fluid-heading-scale.md) — **breaking, behaviour only** (nothing renamed, removed or retyped; every token still resolves): the heading scale is **fluid**. `--mlv-font-size-3xl…6xl` and `--mlv-typography-heading-h{4,5,6}-size` are each one `clamp()` interpolating across `$mlv-viewport-min` (320px, new) → `$mlv-breakpoint-lg` (1200px) instead of stepping at `md` / `lg`, so `theme.scss` now emits **no `@media` block at all** and `tokens.md`'s "Responsive overrides" section is gone with its only four members. The four display tokens keep both endpoints — a phone still gets the old mobile value, a wide desktop the old `lg` one — and move only in between, the largest deviation being at the retired `md` step (`6xl` at 768px is 42.11px where it was 40px). h4/h5/h6 were the only heading roles genuinely fixed at every width; they now ramp too, topping out at exactly the value they used to hold, so a desktop is byte-identical and only a narrow canvas shrinks (h4 is 18px on a phone, was 20px). The ramp is declared on the **semantic heading token**, not on `--mlv-font-size-{2xl,xl,l}`, because those three are shared with the body and UI roles and `--mlv-height-*` is fixed rem — a fluid font inside a fixed-height control clips instead of scaling; the visible edge is that `--mlv-typography-heading-h4-size` no longer equals `--mlv-font-size-2xl` below 1200px, so a stylesheet using the raw step as a stand-in for the h4 size now diverges on a narrow viewport. `3xl` also stops coinciding with `2xl` at the narrow end, which it used to do on purpose: `mlv-page-header` crossfades one grid cell between two title roles, so the gap between the roles **is** the collapse distance, and converging roles reproduce the zero-collapse defect from the other side — `fluid-type.spec.mjs` pins ≥6px for `size="m"` (h2→h4) and ≥3px for `size="s"` (h4→h6) across the band. h1/h2/h3 still resolve `--mlv-font-size-{5,4,3}xl` and inherit the ramp, and `--mlv-font-size-{2xl,xl,l}` plus every body and UI role are unchanged. Consumer action is usually nothing; an app that overrode `$mlv-breakpoint-lg` should know it is now also the **top of every fluid ramp**. New SCSS surface (outside the published package, which ships only the compiled CSS): `$mlv-viewport-min` in `breakpoints.scss` — deliberately **not** a breakpoint, absent from the tier map — and `mixins.fluid($min, $max, $from, $to)`, whose middle term always keeps a `rem` component because a font-size in bare `vw` ignores browser zoom (WCAG 1.4.4, Resize Text).
- [docs/migrations/2026-09-group-form-control-connector.md](docs/migrations/2026-09-group-form-control-connector.md) — **breaking, behaviour only** (nothing renamed, removed or retyped; no barrel, input, output, token or i18n change; `MlvFormControl`, `MlvFormFieldAccessor` and `MlvFormControlLabelTarget` keep the shapes #197 gave them): `mlv-checkbox-group`, `mlv-switch-group` and `mlv-file-upload` now provide `MLV_FORM_CONTROL`, and the two groups take their accessible name from a projected `<mlv-label>`. The ticket's premise — "three components are missing the provider" — is **wrong for two of the three** and the migration says so: only `mlv-file-upload` is an omission (one of 21 `MlvSignalFormUiControlBase` subclasses, the other 20 all provided it); the groups extend `MlvFocusableGroupBase`, a bare roving-tabindex `@Directive()` that holds no value, so nothing was owed. They are fixed anyway, because "not a form control" is not "not the thing a field should resolve": `MlvFormField._control` is `contentChild(MLV_FORM_CONTROL)`, which defaults to `descendants: true`, so with nothing on the group the query walked **past** it and matched the first projected `mlv-checkbox` / `mlv-switch` — a field's `<mlv-label>` named one checkbox out of the set, and its `mlv-message` / `mlv-description` wiring, its `aria-describedby` and its `_controlName()` warnings all reported that child. Four behaviours change at an unchanged API. A projected label's `for` **disappears** (both groups report `labelTarget → { id, labelable: false }` — a `<label for>` names only `button`/`input`/`meter`/`output`/`progress`/`select`/`textarea`, so #197's rule applies and `label.hasAttribute('for')` is the assertion that holds). The groups gain a **real name**: `aria-labelledby` resolves `label() ? _labelId : _fieldLabelId()`, the group's own label winning as the nearer explicitly-authored one — following `MlvRadioGroup` exactly. `aria-label` is **removed** from both, because `aria-labelledby` outranks it and leaving it would have made the field's label lose; `mlv-checkbox-group` was additionally emitting `aria-label=""` whenever `label` was unset, a live empty-name defect. The id lands on a **different node in each** — `mlv-switch-group`'s host, `mlv-checkbox-group`'s inner `<div>` — because that is where each writes `role="group"`, and a spec pins it. Adjacent, and the reason to read § 3: satisfying `MlvFormControl` costs nine public members the groups do not use (the interface requires ten; they already had `state`), so `group.disabled()` on a `viewChild(MlvCheckboxGroup)` **used to be a compile error and now compiles and always answers `false`** — a change from loud to silent. None is an `input()`, so `[disabled]="…"` on the element still fails AOT with NG8002; read `computedDisabled()` on the individual children. Hiding them is not available (`implements` requires public members, and widening the interface would break every `inject(MLV_FORM_CONTROL).focused()` under `strictNullChecks`), and a `useFactory` adapter object was rejected because it cannot inject its own host and degrades `_controlName()` to `"Object"` in both dev warnings. **No in-repo markup changes** — nothing in `libs/` or `apps/docs` renders any of the three inside a field. Left open deliberately: `label` / `ariaLabel` remain **inert** on `mlv-file-upload`, which renders no `<mlv-label>` and whose only AT entry point is the browse `<button>`; naming it would override `actionLabel()`, and the same shape recurs on `mlv-rating`, whose `[attr.aria-label]="_i18n().rating"` host binding silently overrides a consumer's `ariaLabel` outright.
- [docs/migrations/2026-09-popup-tooltip-rtl-inline-offsets.md](docs/migrations/2026-09-popup-tooltip-rtl-inline-offsets.md) — **breaking, behaviour only** (nothing renamed, removed or retyped; `POPUP_POSITION_MAP` and `TOOLTIP_POSITIONS` are unchanged in **value** — the diff on `popup-positions.ts` is JSDoc only): `ConnectedPosition.offsetX` is now **logical** and mirrors in RTL. CDK's `FlexibleConnectedPositionStrategy` mirrors `originX` / `overlayX` against the pane's direction but returns `offsetX` verbatim from `_getOffset()` — applied both as `x += offsetX` while scoring a candidate in `_getOverlayFit` and as `translateX(${offsetX}px)` on the pane, with no `_isRtl()` anywhere on that path. So the 8px gap the `left-*` / `right-*` entries expressed (and the tooltip's ±6) kept pushing the panel the same way on screen after mirroring moved it to the trigger's other side: measured, a `right-start` popup under a scoped `[dir="rtl"]` moved its anchor `left: 0` → `right: 0` while `translateX(8px)` stayed put, turning the gap into an overlap — a 2x error. A new `mlvMirrorInlineOffsets(positions, direction)` in `@malva-ui/cdk/utils` is applied by `MlvPopupService.open()` and `MlvTooltip._show()` with **the same direction the pane is created with**, and re-applied by the popup whenever the direction flips under an open overlay or `setPositionOrigin` swaps the list — `updatePosition()` alone re-applies whatever list the strategy still holds. It returns its input **by reference** when nothing changes, because CDK dedupes `positionChanges` by the _identity_ of the chosen `ConnectedPosition`. `offsetY` is the block axis and is never touched. The rejected alternative — a logical `margin-inline-*` on the panel — is rejected for the **right** reason, recorded because the obvious one is measurably false: a margin is _not_ invisible to CDK (it inflates the `box-sizing: border-box` pane rect `_getOverlayFit` scores by exactly its own size) and `margin-inline-*` _does_ mirror. It fails because the gap belongs to whichever side the **resolved** position chose, and `left-*` / `right-*` are fallback twins in one list that one margin cannot serve — a per-position `panelClass` arrives after scoring, and a symmetric `margin-inline` inflates the pane on both sides and adds a spurious gap to every `top-*` / `bottom-*` entry. **No in-repo markup changes, but shipped chrome moves in RTL:** `mlv-sidebar-group` / `mlv-sidebar-item` (`position="right-start"`, +8, a 16px correction on permanent navigation chrome), the four pickers that write no position input and therefore fall back to all twelve map entries (`mlv-day-picker`, `mlv-date-range-picker`, `mlv-time-picker`, `mlv-color-picker-popup`), and submenus, whose `SUBMENU_POSITIONS` flips the side itself. Unaffected and worth stating: `DROPDOWN_POSITIONS` (select, combobox, autocomplete), `MENU_POSITIONS`, `CONTEXT_MENU_POSITIONS`, speed-dial and the scheduler month popover carry no `offsetX` at all. The one shape that **regresses** is a consumer who already worked around #180 by hand — `offsetX: dir === 'rtl' ? -8 : 8` now double-flips; delete the conditional and write the LTR sign. There is deliberately no opt-out, since one would re-legalise the half-logical position the change removes; a genuinely physical gap is `margin-left` / `margin-right`, **not** `margin-inline-*`.
- [docs/migrations/2026-09-list-item-group-collapsed-inert.md](docs/migrations/2026-09-list-item-group-collapsed-inert.md) — **breaking, behaviour only** (nothing renamed, removed or retyped; no barrel, input, output, token, i18n key or BEM class changes, and the stylesheet is byte-identical): a collapsed `mlv-list-item-group` now leaves the tab order and the accessibility tree. `.mlv-list-item-group__content` gains `[attr.inert]="_contentVisible() ? null : ''"` — one binding, no CSS. The group collapsed entirely in CSS and always had (`grid-template-rows: 0fr` plus `overflow: hidden` / `opacity: 0` on the inner wrapper), and **none of those three removes anything from the a11y tree**: a zero-height clipped box still computes `visibility: visible`, so AT read every row of a collapsed section out under a toggler announcing `aria-expanded="false"`, and Tab landed on links inside it **with no focus ring anywhere on screen** — WCAG 2.4.3 / 2.4.7 / 1.3.1. The whole difficulty is the predicate, and it is not the one #221 anticipated: since #220 `variant="inset"` pins content open through `--pinned` **independently** of `--toggled`, so a pinned group renders on screen with `_expanded()` false and the obvious `[attr.inert]="!_expanded()"` would mark every inset section's **visible** rows inert — dropping every `mlv-switch` in `apps/docs` list example 8 out of the tab order. It fails in the direction that hides itself: `open` coerces now, so both shipped docs examples write the bare `open` attribute and carry `--toggled` _and_ `--pinned`, and a spec written against them would pass while `list.spec.ts`'s un-`open`ed `InsetListGroupsHost` broke. Hence a named `_contentVisible = _expanded() || _pinnedOpen()` carrying the warning in its JSDoc, and a four-state attribute contract in the specs. #221 frames this as a timing problem — "timed against the `grid-template-rows` transition, and the reduced-motion path has to stay correct" — which is true of `visibility` / `display` / `hidden` and **false of `inert`**, which is not a rendering property: it flips with the state and the transition runs underneath, needing no `transition-delay` and so no reduced-motion path (measured: the t=100ms `grid-template-rows` sample is byte-identical with and without `inert`). `visibility` would have owed a hand-written reduced-motion reset no other component has, because `mixins.reduced-motion()` overrides `transition-duration` but **not** `transition-delay`; `hidden="until-found"` computes to `content-visibility: hidden` and destroys the transition outright. **No axe sweep is added, because measurement shows none can see this** — a collapsed group holding a focusable `<a href>` sweeps clean without `inert`, and so does a **visible** pinned group wrongly marked `inert`; the four existing sweeps are kept and pass unchanged, which is what shows that dropping a `role="list"` region out of the tree raises no `aria-required-children` / `aria-required-parent` / `aria-valid-attr-value` fallout. Nobody in this repository is affected and nothing renders differently. Consumer-visible edges, all documented: `.focus()` into a collapsed group is now **blocked** while `.click()` / `dispatchEvent()` are **not** (measured — `inert` blocks hit-testing, which synthetic dispatch bypasses; both bubble out and default activation still navigates), and collapsing a group **while focus is inside it** now drops focus to `<body>` a frame or two later — the one place the change makes something worse, reachable only by a programmatic close or a control inside the region calling `toggle()`, with no focus restoration wired deliberately (the toggler is the only candidate and moving focus there on a state change the user did not initiate is its own WCAG 3.2.1 problem). Adjacent: `mlv-expand` looked like a fourth `inert` precedent and is not — its binding sits inside `@if (opened())` so the ternary can only ever yield `null`, dead code whose `CLAUDE.md` described it as live behaviour; that paragraph is corrected here and the binding itself is #263.
- [docs/migrations/2026-09-form-utils-testing-runner-agnostic.md](docs/migrations/2026-09-form-utils-testing-runner-agnostic.md) — **breaking, behaviour only** (nothing renamed, removed or retyped; `verifyFormsBinding` keeps its signature and its four expectations): `@malva-ui/core/form-utils/testing` no longer imports `vitest`. It is a published entry point — its own `ng-package.json`, so ng-packagr builds it and `dist/libs/core/package.json` exports the subpath — and the FESM bundle shipped in `@malva-ui/core@0.1.15` opens with `import { expect } from 'vitest'`, which core declares in neither `dependencies` nor `peerDependencies`. A consumer on Jest, Karma or Web Test Runner therefore got `Cannot find module 'vitest'` at build time with no install-time signal; a consumer on Vitest worked only by coincidence. Invisible in-repo, because all twenty-odd `*-binding-matrix.spec.ts` files resolve `vitest` from the workspace root manifest — it was found by #242's `scripts/check-package-dependencies.mjs` and held as that guard's single `DECLARATION_EXCEPTIONS` entry, which this change **deletes**, leaving the list empty. Declaring it lost on every reading: a required peer installs a test runner into every consumer app, an optional peer is not installed by npm at all (and core deliberately carries no `peerDependenciesMeta`), `allowedNonPeerDependencies` is an ng-packagr build option that never reaches the published manifest, and unpublishing an exported path is a major owing a deprecation window. So the import is **gone** instead: comparison is now `fast-equals`' `deepEqual` (already a declared core `dependency`) and `===`, and a failed expectation throws an `AssertionError`-shaped error the entry point constructs — `name`/`actual`/`expected`/`operator`/`showDiff`, the shape Vitest's reporter special-cases, so a Vitest consumer keeps the identical expected/received diff while every other runner reads both values off the message, which now carries them. `toEqual` and `fast-equals` are not the same relation, so the migration carries the **measured** divergence table rather than a count: key sets, prototypes and realms read stricter (an own `undefined`-valued property is no longer treated as absent, a class instance no longer equals a same-shaped plain object), `-0`/`+0` reads **looser** (SameValueZero), and code that read a Vitest-internal field (`matcherResult`, `diff`) off the rejection sees `undefined` — `name`/`message`/`actual`/`expected`/`operator` are the documented shape. Two cases needed code, not just prose: `fast-equals` maps no comparator to the `[object File]` / `[object Blob]` tags and falls through to `false`, so **no two distinct `File`s were ever equal** — which would have made `mlv-file-upload`'s matrix permanently red the moment its control stopped handing back the identical object, with a message reading `{}` because a `File` has no enumerable own properties — so the helper adds a `name`/`size`/`type`/`lastModified` comparator (contents deliberately unread: `File.text()` is async), which is also stricter than `toEqual`, whose answer for two `File`s with _different_ names was `true`; and the plain `deepEqual` overflows the stack on a cyclic value, turning a failed expectation into a `RangeError` naming no binding mode, so the **circular** comparator is used instead — measured at 2.44x per comparison and 0.015 ms across all ~500 matrix assertions in the workspace, which retires the only argument against it. Nobody on Jest/Karma/WTR loses anything — the entry point did not resolve for them at all.
- [docs/migrations/2026-09-list-item-group-open-coercion.md](docs/migrations/2026-09-list-item-group-open-coercion.md) — **breaking** (no exported symbol renamed or removed; the `@malva-ui/core/list` barrel is unchanged): `mlv-list-item-group` fixes two defects that cancelled each other out on screen. `open` was the workspace's only `model<BooleanInput>` and carried **no** `coerceBooleanProperty`, so the documented `<mlv-list-item-group open>` bound `''` and read falsy — and `toggle()` on such a group **opened** it, since `!''` is `true`. `model()` accepts no `transform` (`ModelOptions` is `alias` + `debugName` only), so `open` is now `input<boolean, BooleanInput>(false, { transform: coerceBooleanProperty })` plus an explicit `openChange` `output<boolean>()`, with a `linkedSignal` holding the resolved state so a user toggle still survives a one-way `[open]` — `model()`'s semantics, written out. `[(open)]`, `(openChange)` and `[open]` all bind exactly as before and `open()` narrows `BooleanInput` → `boolean`; only `groupRef.open.set(v)` from TypeScript stops compiling. Independently, `variant="inset"` pinned the content open in CSS with no dependency on `--toggled` and hid the chevron, so an inert `<button aria-expanded="false">` sat in the tab order over content that was permanently on screen — a live WCAG 4.1.2 / 1.3.1 defect on `apps/docs` list examples 5 and 8, invisible to visual QA precisely because the falsy `open` and the pinning cancelled. `MlvList` now provides an **internal** `MLV_LIST` token (deliberately not exported) carrying its `variant`; a group that resolves `inset` stamps the new `.mlv-list-item-group--pinned` modifier and renders `.mlv-list-item-group__label` — inert text naming the content region through `aria-labelledby` — **instead of** `.mlv-list-item-group__toggler`, which is not removed and is still the toggler in every non-inset list. The open-state CSS moved onto `--pinned` rather than staying a `.mlv-list--inset` descendant match, because DI is lexical and CSS is DOM: a group merely _projected_ into an inset list resolves no list, and must stay genuinely collapsible rather than reproduce the contradiction. Geometry is unchanged — `--pinned` carries the same `grid-template-rows: 1fr` / `opacity: 1` / `overflow: visible`, and the `__label` rule is the old `__toggler` rule verbatim (`pointer-events: none` included) — but the **typeface is not**: there is no global `button { font: inherit }` reset in `libs/styles` and `__toggler` never wrote one, so the band rendered in the UA button font (`Arial` on Chrome/macOS) while the `<div>` inherits `--mlv-typography-family-text` from `mixins.base()` on the host. `line-height` pins the block size, so nothing reflows; the label simply moves into the brand face, which is the intended look but is a real visible delta. Breaks CSS written against `.mlv-list--inset .mlv-list-item-group__toggler` (retarget to `__label`) and anything that clicked or focused that button; every group in the workspace is inset, so no rendering changes here. Forward-facing, the migration doc also records the one arrangement whose rendering _does_ change — a group **projected** into an inset list, which resolves no `MLV_LIST`, so it keeps a plain-variant toggler and a collapsed card because three further rules (`__content`'s `grid-template-rows`, its `> div` `opacity`/`overflow`, and `__arrow { display: none }`) left the `.mlv-list--inset` scope with the rename — the inverse DI-yes/DOM-no case, and the fact that `.mlv-list--inset .mlv-list-item-group--toggled` now matches for the first time because `open` finally coerces.
- [docs/migrations/2026-09-layout-removal.md](docs/migrations/2026-09-layout-removal.md) — **breaking:** the secondary entry point `@malva-ui/core/layout` is **deleted**, with no alias. It had no body — `mlv-layout` itself went with the `mlv-page` rebuild and what remained was one line, `export * from '@malva-ui/cdk/theme';` — so the consumer action is an import-path edit and never a code change: `MlvThemeService`, `provideDefaultTheme`, `MLV_THEME`, `MLV_THEME_KEY`, `MlvTheme`, `MlvThemeMode`, `defaultTheme` and `defaultThemeKey` keep their names, their types and their object identity, and the persisted `mlv-theme` key and encoding are unchanged, so a moved import keeps every user's saved choice. # General Guidelines for working with Nx

- For navigating/exploring the workspace, invoke the `nx-workspace` skill first - it has patterns for querying projects, targets, and dependencies
- When running tasks (for example build, lint, test, e2e, etc.), always prefer running the task through `nx` (i.e. `nx run`, `nx run-many`, `nx affected`) instead of using the underlying tooling directly
- Prefix nx commands with the workspace's package manager (e.g., `pnpm nx build`, `npm exec nx test`) - avoids using globally installed CLI
- You have access to the Nx MCP server and its tools, use them to help the user
- For Nx plugin best practices, check `node_modules/@nx/<plugin>/PLUGIN.md`. Not all plugins have this file - proceed without it if unavailable.
- NEVER guess CLI flags - always check nx_docs or `--help` first when unsure

## Scaffolding & Generators

- For scaffolding tasks (creating apps, libs, project structure, setup), ALWAYS invoke the `nx-generate` skill FIRST before exploring or calling MCP tools

## When to use nx_docs

- USE for: advanced config options, unfamiliar flags, migration guides, plugin configuration, edge cases
- DON'T USE for: basic generator syntax (`nx g @nx/react:app`), standard commands, things you already know
- The `nx-generate` skill handles generator discovery internally - don't call nx_docs just to look up generator syntax
