# Library: autocomplete

> **Keep this file up to date.** Update whenever the `[mlvAutocomplete]` directive's API, behaviour, dependencies, or the shared matcher it consumes change.

## Overview

`@malva-ui/core/autocomplete` provides a single reusable attribute directive, **`[mlvAutocomplete]`**, that adds autocomplete / typeahead behaviour to **any** text input — a native `<input>` or a `<mlv-input>` — without turning the field into a form control. It reuses the same building blocks as `mlv-combobox`: the shared substring **matcher** (`filterOptions` / `defaultOptionMatcher` from `@malva-ui/core/dropdown`), the **`mlv-dropdown-panel`** suggestion list, and the shared **`MlvOptionsAdapter`** source engine.

The directive is the new surface for arbitrary inputs; `mlv-combobox` remains the full `FormControlBase` combobox. Both now share one matching implementation.

## `MlvAutocomplete<T>`

**File:** `libs/core/autocomplete/src/lib/autocomplete/autocomplete.ts`
**Selector:** `[mlvAutocomplete], [mlvAutocompleteSearch]`
**exportAs:** `mlvAutocomplete`

Attribute directive — no template. It renders the suggestion popup via a CDK **overlay hosting a `mlv-dropdown-panel` component portal** (a headless attribute directive cannot host `mlv-popup`'s declarative `ng-template mlvPopupContent`; the overlay is the same CDK primitive `mlv-popup` itself wraps). The panel is reused unchanged for list rendering, option groups, aria listbox semantics, and the activedescendant highlight.

### Behaviour / accessibility

- **Input resolution:** the directive resolves the real focusable `<input>` — the host itself when it is an `<input>`, otherwise the inner `<input>` of a projected `mlv-input` (`querySelector('input')`) — and wires ARIA + listeners onto it via `Renderer2`.
- **WAI-ARIA combobox:** `role="combobox"`, `aria-expanded`, `aria-controls` (the panel's listbox id), `aria-activedescendant` (the active option id), and `aria-autocomplete` — `both` while inline completion is on (default), `list` when opted out (`[mlvAutocompleteInline]="false"`).
- **Listbox accessible name (#222):** the panel's inner `role="listbox"` is named after the **host input**, so it shares the accessible name of the field it belongs to — the same contract `mlv-select` / `mlv-combobox` express as `label() || ariaLabel()`, except the field here is the consumer's, so the name is read off the DOM rather than off an input. `_resolveHostAccessibleName()` follows the accessible-name computation's order for a labelable control: `aria-labelledby` (2B) → `aria-label` (2C) → the input's associated `<label>`s (2D), skipping `aria-hidden` subtrees so an `mlv-hint`'s hidden source text stays out. `title` / `placeholder` are deliberately **not** consulted (last-resort sources; a placeholder-derived name is a WCAG smell the library must not launder). Every naming source is flattened to a _flat string_ (whitespace collapsed, then trimmed), `aria-label` included, because the accessible-name computation normalizes once over whichever source it takes — so the panel and the field it is named after cannot disagree on `aria-label="Fruit  basket"`. Re-resolved **on every query while the popup is open**, not once per overlay: `_openPopup()` is re-entered from `_runQuery()` on each debounced keystroke, while the overlay — and with it the panel component — is created on the **first** open of a session and disposed on close. The `.set()` therefore sits deliberately **above** `_openPopup`'s `if (!this._overlayRef)` guard; moving it inside would read as "once per open" but pin the name for the whole session, so a label that changes while the popup is up (a locale switch, an `@if`-swapped `<label>`) would keep the old name until it closed. Per query bounds staleness at the next keystroke; closer than that would need a `MutationObserver` over DOM the directive does not own, deliberately not added. Pushed through the existing `MlvDropdownPanel.ariaLabel`: no new public API on either side, and no i18n fallback string — the `autocomplete` slice (#370) carries messages, not a name, because a fallback name would paper over an unnamed field. An unnamed host input resolves to `null`, so **no** `aria-label` attribute is emitted rather than an empty one: a nameless `role="combobox"` input is the consumer's own WCAG 4.1.2 defect and naming its popup would only make it harder to see. This is a **consistency** fix, not an axe fix — axe's `aria-input-field-name` exempts a listbox that any `role="combobox"` points at through `aria-controls` / `aria-owns` (`isComboboxPopup` inside `no-naming-method-matches`), which is precisely this wiring, so the rule reports `inapplicable` either way.
- **Inline completion (`inline`, default on):** on each user **insertion** (input event where text grew — never Backspace/Delete/cut/paste-shrink), when the caret is a plain cursor at the end of the field and the **top visible result's label is a genuine case-insensitive prefix** of the typed text, the directive inserts that suggestion's remainder after the caret and leaves it **selected** (typed prefix keeps the user's casing; remainder uses the suggestion's). Continuing to type replaces the selection (browser default); `Enter`/click commits the full value (caret to end); `Escape` strips the completion back to the typed text (then the existing close-then-clear semantics). Backspace/Delete do not re-complete until the next insertion. Non-prefix (fuzzy/substring-only) top matches are skipped silently — list-only. The completed top item (index 0) becomes the activedescendant-active row. Insertion-vs-deletion is detected via `beforeinput` `inputType` when available, else a value-length comparison (jsdom/programmatic). Remote sources: the completion is **armed** for the query and applied by the adapter-mirroring effect once items arrive and the source is no longer loading, then disarmed — so it fires once, from the current query's results, never from a stale in-flight one. The completed value is propagated through the same synthetic-`input` dispatch a commit uses, so `mlv-input` / `ngModel` / a form control observe it (the directive suppresses re-filtering that one event).
- **Activedescendant keyboard model:** DOM focus stays in the input. ArrowDown/ArrowUp open then move the highlighted option (wrap-around); Home/End jump to first/last; Enter selects the highlighted option; Escape closes, then (already closed) clears the input. A **readonly host `<input>`** makes the directive inert, like `disabled` (#301): it reads `el.readOnly` live, so no suggestions open, Escape no longer writes `''` into a field the user may not edit, and `selectFromPanel()` refuses a pick that lands after the host turned readonly or disabled (it closes the popup and writes nothing). A popup already open when the host locks still **closes on Escape** — the one key an inert directive handles, since closing writes nothing; it neither strips an inline completion nor clears the field there — and an inline completion armed by typing is **not applied** when remote results land after the lock. The active-index state + wrap navigation is the shared `MlvActiveDescendant` class from `@malva-ui/core/dropdown` (`new MlvActiveDescendant(() => this._results().length)`) — the identical engine `mlv-combobox` uses (both previously carried a byte-identical private `_moveActive`). The `aria-activedescendant` id comes from the shared `optionId(this._listboxId, index)` helper, matching the id the panel stamps.
- **Selection:** committing writes the option label into the input and dispatches a synthetic `input` event (so `mlv-input` / `ngModel` stay in sync — the directive suppresses re-filtering that one event), emits `optionSelected`, sets `selectedValue`, and closes. Pointer selection needs **no aria reconciliation guard** because the panel is never seeded with a committed selection (`selectedValues` is always `[]`), so any non-empty `valueChange` is a genuine pick.
- **Source engine (`MlvOptionsAdapter`):** every `options` shape plus the `search` fn is normalised by the shared adapter from `@malva-ui/core/dropdown` (`new MlvOptionsAdapter({ source: this.options, searchFn: this.search, debounce: signal(0), eager: signal(false) })` — `debounce` is `0` because the directive already debounces keystrokes before `_runQuery`). Its `mode()` picks the query path:
  - **local** (`T[]` / `Observable<T[]>`) — `_runQuery` resolves + filters `adapter.items()` synchronously with `matcher`, exactly as before, and opens the panel.
  - **remote** (`MlvDataSource<T>` / `search` fn) — `_runQuery` first **seeds** the results from whatever `adapter.items()` already holds, opens the panel, then runs `adapter.search(query)`. A data source receives the query as `setSearch({ query, keys: [] })` (natural-field search — the directive knows option shapes, not column keys) and owns its own filtering; the directive never re-filters remote items with `matcher`.
  - One constructor `effect` mirrors `adapter.items()` into the rendered results for **both** modes: remote items render as-is, local ones are re-filtered against the current query (with the activedescendant reset if the highlighted row no longer exists). The local arm is what repaints an already-open panel when an `Observable` source emits late — nothing else would, until the next keystroke — and it is skipped while the panel is closed, since `_runQuery` fills it on open. Because the effect only fires on an item-set **change**, it is also why the remote arm of `_runQuery` seeds: a `search` fn that memoises and returns the identical array for a repeated query would otherwise leave the panel empty after the `minLength` gate cleared the results. Binding a stable `search` function reference is still recommended (an inline arrow is a fresh reference on every change-detection run) — the adapter tolerates re-binding without cancelling an in-flight call, but a stable reference keeps the bookkeeping trivial.
- **Debounce + stale results:** keystrokes are debounced (`debounce`); a remote source shows the panel's loading affordance (`--loading` recede + `role="status"` row) while the **previous results stay rendered and interactive** rather than blanking to an empty list, and the adapter's monotonic token discards a superseded in-flight result. Local sources never report loading.
- **Lazy paging (data source only):** `hasMore`, `loadingMore` and `infiniteScrollThreshold` are pushed into the panel, whose scroll sentinel emits `loadMore`; the directive forwards that to `adapter.loadMore()`, which appends the next page slice (and is a no-op until the requested page has landed, so a repeatedly firing sentinel cannot skip a page).
- **Result normalization:** array, Promise, and Observable search results are
  normalized by the pure `toOptionsResult()` helper from
  `@malva-ui/core/dropdown` (it started out directive-private and moved so every
  option control shares one async boundary) — the adapter now owns that call, so
  the directive no longer imports it and stays focused on interaction state.
- **No results (#370):** with the popup open, nothing loading and zero results, the panel shows a "No results found" row (`.mlv-dropdown-panel__empty`, text from `autocomplete.noResults`). The directive builds the row once per overlay and projects it into the panel's `[mlvDropdownPanelEmpty]` slot (`projectableNodes` `[[], [row]]`), which renders it **after** the listbox: the same row inside an option-less `role="listbox"` fails axe `aria-required-children`. Its text is written by a constructor `effect` (`Renderer2.setProperty(row, 'textContent', …)`), so a language switch re-words an open panel.
- **Results announcement (#370):** mirrors `mlv-combobox` — a polite announcement of `autocomplete.resultsAvailable` (ICU plural `{count}`, "3 results available") or `noResults` whenever the open panel's result count changes, and nothing while a search is in flight (so a remote search never announces "No results found" before its results land). The directive has no template of its own, so it announces through CDK `LiveAnnouncer.announce(message, 'polite')` rather than combobox's visually hidden `role="status"` region; a `computed` over (open, loading, count, wording) feeds one `effect`, so an unchanged message is not re-announced.
- **Dismissal:** backdrop-less overlay; a `mousedown` on the panel is `preventDefault`ed so option clicks don't blur the input, and `outsidePointerEvents` closes on genuine outside clicks (the host is treated as inside).

### i18n

Since #370 the directive reads the optional `autocomplete` slice of `MlvLanguage` through `MLV_AUTOCOMPLETE_I18N` — `noResults`, `loading`, `resultsAvailable` (ICU `{count}`), every key optional — resolved with `MlvI18nResolverService` in the pack's `MLV_LOCALE`. The token is injected `{ optional: true }` and every key falls back to English (`OPTIONAL_MESSAGE_FALLBACKS`), so the directive still forces no provider: with no `provideMlvI18n()`, or under a hand-written pack without the slice, it renders and announces exactly the English it would have. Every shipped pack words the slice exactly as its own `combobox` slice (pinned by `locale-contract.spec.ts`), so a field reads the same with `mlv-combobox` or `[mlvAutocomplete]`. `loadingText` still wins when bound.

## Usage

```html
<!-- Static options on a plain mlv-input -->
<mlv-input label="Fruit" [mlvAutocomplete]="fruits" (optionSelected)="pick($event)" />

<!-- Async search (min length 2) with loading + highlighting -->
<mlv-input label="User" [mlvAutocompleteSearch]="searchUsers" [mlvAutocompleteMinLength]="2" [mlvAutocompleteToOption]="userToOption" />

<!-- Data source: it filters (setSearch) and pages itself; the panel shows a
     spinner over the previous results and appends the next page on scroll -->
<mlv-input label="Assignee" [mlvAutocomplete]="usersDataSource" [mlvAutocompleteMinLength]="2" [mlvAutocompleteToOption]="userToOption" />

<!-- Custom matcher (prefix match) -->
<mlv-input [mlvAutocomplete]="cities" [mlvAutocompleteMatcher]="startsWith" />

<!-- Opt out of inline completion (list-only, aria-autocomplete="list") -->
<mlv-input [mlvAutocomplete]="fruits" [mlvAutocompleteInline]="false" />

<!-- Native input also works -->
<input mlvAutocomplete [mlvAutocomplete]="fruits" />
```

## Suggestion panel width (#150)

- The field's measured width is a **floor**, not a fixed width: `OverlayConfig.minWidth`, never `width`, so a suggestion longer than the field grows the panel instead of being clipped.
- Ceiling with no author value = the viewport. `withFlexibleDimensions(true)` sizes the bounding box to the space up to the viewport edge, and CDK's `.cdk-overlay-pane { max-width: 100% }` caps the pane inside it.
- `mlvAutocompleteMinWidth` raises the floor; `mlvAutocompleteMaxWidth` tightens the ceiling. Neither can widen what it constrains:
  - `_resolveMinWidth(el)` emits `max(<field>px, <authored>)`, so a value under the field width loses to the field.
  - a `mlvAutocompleteMaxWidth` wider than the viewport is still clamped by the bounding box.
- **The floor outranks both ceilings.** CSS resolves the used width as `max(min-width, min(max-width, width))` — `min-width` is applied last and wins. So a `mlvAutocompleteMaxWidth` below the effective floor is silently ignored (and the panel renders past its bounding box, which has no `overflow: hidden`), and a `mlvAutocompleteMinWidth` wider than the space to the viewport edge pushes the panel off-screen — `.cdk-overlay-pane { max-width: 100% }` governs _content_-driven growth only.
- The `max()` is deliberate — the field is measured in px, the author value may be in any unit. Emitting both sides lets the browser resolve them; converting here would freeze the author value against the root font size at open time. **`%` is the exception and is not supported**: the pane is a `static` flex item of the bounding box under flexible dimensions, so a percentage resolves against the free space to the viewport edge rather than anything the author can predict. `ch` resolves against the pane's own font, not the suggestion rows'.
- Under flexible dimensions **with `withPush(false)`** (hard-coded at `autocomplete.ts`'s strategy build) CDK **clears `max-width` on the pane** and applies `OverlayConfig.maxWidth` to the bounding box; `_hasExactPosition()` is `!_hasFlexibleDimensions || _isPushed`, so with push enabled the cap would move back onto the pane. Specs assert the cap on `.cdk-overlay-connected-position-bounding-box`, the floor on `.cdk-overlay-pane`.
- The overlay is created per open (disposed on close), so both values are read fresh each time — no stale first-open measurement.
- Same contract in `mlv-select` / `mlv-combobox` as `dropdownMinWidth` / `dropdownMaxWidth`.
- **How far it may grow depends on which field edge is anchored (#154).** The strategy is built with the shared `DROPDOWN_POSITIONS` from `@malva-ui/core/dropdown` (replacing the directive's private `AUTOCOMPLETE_POSITIONS`) — start-aligned below/above preferred, end-aligned below/above as the inline fallback — so a narrow field near the viewport's inline-end edge anchors its panel's inline-end edge to the field and grows back toward inline-start instead of being boxed into the sliver after it. See `libs-dropdown.md` → _Overlay positions (#154)_.

## Testing

- Nx project: **`core-autocomplete`** — `yarn nx test core-autocomplete` (Vitest).
- The result-normalization helper is covered where it now lives: `options-result.spec.ts` in **`core-dropdown`** (`toOptionsResult`).
- **Suggestion listbox accessible name (#222)** — its own `describe` with a host whose naming source is switchable: the listbox takes its `aria-label` from the input's `aria-label`, from a native `<label for>`, and from `aria-labelledby`, and emits **no** attribute when the input is itself unnamed. Two more pin the resolution _policy_ rather than a source: the name is re-resolved **on each query** (the panel node is asserted unchanged across the keystroke, so it is a re-resolve on the live panel and not a fresh open — the tripwire for moving the `.set()` inside the overlay guard), and the `aria-label` branch collapses internal whitespace like every other branch. Alongside them, one test pins the `role="combobox"` + `aria-controls` → listbox-`id` wiring, because that wiring is exactly what makes axe's `aria-input-field-name` `inapplicable` here — so the axe sweep below cannot be the regression guard for the name and must not be re-tightened into one.
- **Listbox name from an `mlv-input` host** — a second `describe`, because every real consumer (all four `apps/docs` examples, and the shape `best-practices.md` mandates for any text field) writes `<mlv-input>`, never a bare `<input>`, and that resolves through a different branch: the directive walks to the **inner** native input, whose `labels` collection holds `mlv-label`'s rendered `<label for>`. Covers `mlv-input`'s own `label` input, the same field inside an `mlv-form-field` with a projected `<mlv-label>`, and — the case the native-`<input>` tests structurally cannot see — that an `mlv-hint`'s text stays **out** of the name (it renders inside the `<label>` and is kept out only by its `aria-hidden` source span; un-hiding it names the panel `'Fruit pick one'`).
- **Axe** — full sweeps of `document.body` (the panel is portalled into the CDK overlay container, outside the fixture) through `expectNoAxeViolations`, one per panel state that changes the markup: populated, the in-flight `loading` row (`role="status"` + `aria-busy` on the listbox), an empty result list (the "No results found" row after the listbox — the sweep asserts the row is there), and the panel open under RTL (the overlay pane is its own `[dir]` scope). Not yet swept: the `loadingMore` next-page row, whose markup is the `loading` row's (`role="status" aria-live="polite"` + spinner + text) at the other end of the panel, and which needs the paged data-source stub. #222 retired the project's `ROLLOUT_PENDING` entry in `scripts/check-axe-coverage.mjs` because a partial sweep had no other shape then; #257 gave it one, so the entry is back as `{ project: 'core-autocomplete', owes: ['the `loadingMore` next-page row (needs the paged data-source stub)'] }` and the gap is tracked by the guard rather than only here.
