How these numbers are measured

Nothing here is a published result from another machine. The page runs its own measurements in your browser when you open it and when you press the benchmark buttons, so the numbers describe your hardware, browser, display and current system load. They are not comparable with numbers taken anywhere else, and two runs on the same machine will differ.

The dataset

Rows are generated, never shipped. A seeded 32-bit PRNG (mulberry32) produces the accounts from a fixed seed using only integer operations, so the same row count yields byte-identical data in every browser, on every machine, across reloads — and growing the dataset extends it rather than reshuffling it. No fixture file is committed, and no generated value depends on the clock, the locale, or Math.random().

Where the work happens

The dataset lives inside a Web Worker. Search, column filters, sort and paging run there, using the same semantics as the library's own MlvArrayDataSource — search ORs across the searchable columns, filters are ANDed, strings compare through Intl.Collator with numeric collation, and the total is counted before paging. The main thread receives one postMessage per query and does nothing but render it.

Initial render

Measured from the moment the first rows reach the main thread to the first animation frame after Angular has written them to the DOM — change detection, DOM updates, layout and paint for the rows that are actually visible, not for the whole dataset. The end-to-end figure beside it adds everything before that: generating the dataset, running the first query, the artificial latency, and the structured clone.

A hidden tab stops receiving animation frames altogether, so a sample whose rows arrive while you are looking at another tab is discarded rather than reported as a several-second render. The opening query is re-run once the page becomes visible, so this number is always taken with the table on screen.

Scroll frame rate

The benchmark scrolls the table from inside an animation-frame callback for two seconds and records when each frame ran. Frames per second is the number of intervals observed divided by their total span; the mean and 95th-percentile frame times are reported next to it because an average hides a stutter. The rate is capped by your display — 60 fps on a 60 Hz panel is the ceiling, not a mediocre score — so the quickest frame of the run is reported beside it as the bound the result should be read against. That bound is an observation, not a hardware reading: frame timestamps jitter, so it can sit slightly above the panel's true refresh rate. A hidden tab receives no frames at all, so the benchmark refuses to sample one. It also refuses when your system asks for reduced motion: the run is two seconds of scrolling you did not ask for, and a run that does not scroll would measure an idle page rather than the table.

Filter latency

Measured from the moment a filter or search is committed to the first frame that shows the result, and broken into the four places the time actually goes: computing the query in the backend, the artificial latency you dialled in, the structured clone that carries the rows across, the main-thread pass that restores row identity, and the main-thread render. The compute number is taken around the query pass alone and finishes before the artificial delay starts, so the delay can never inflate it.

Row identity is measured separately because it is main-thread work proportional to the delivered rows, and in virtual-scroll mode the delivered rows are the whole result set. Every arriving row is looked up by id so the instance already on this thread is reused — which is what keeps a selection and an expanded tree row alive across a sort — and that walk is reported rather than left in the gap between the transfer and the render.

What these numbers do not prove

  • In virtual-scroll mode the table asks its source for every matching row, so paging is not server-side there and the transfer number is the cost of moving the whole result set. Switch to server-side paging to see the other trade.
  • Virtual scroll has a hard ceiling that has nothing to do with the table: a viewport reserves rowHeight × rowCount pixels of scrollable height, and browsers stop scrolling at about {{ maxScrollablePx | number }} CSS pixels — roughly {{ maxVirtualRows | number }} rows at {{ rowHeight }} px each, fewer under a larger browser font size, because rows are sized in rem. Above that this page pages on the backend instead, and says so, because the alternative is a table whose tail silently cannot be scrolled to.
  • Transfer is a real, unavoidable main-thread cost: the structured clone is deserialised on this thread. It is reported separately rather than folded into "backend" time.
  • The backend is a Web Worker, not a network service. It proves the table's data-source contract and the main thread's workload; it says nothing about a real server's query planner.
  • Row identity is preserved across refetches, which is what lets selection and expanded tree rows survive a sort or a filter. That is a property of this data source, not of the table.
  • Row selection is offered in server-side paging mode only. With virtual scroll on, mlv-data-table renders its rows inside a role="presentation" table, where aria-selected would be an ARIA attribute the row's role does not support — so this page does not ask for it there.
